## `/quant` 頁面：從陽春到 XQ 式的完整迭代

這段是連續好幾輪「做一版→實測→發現不夠好→再修」，記重點跟踩到的坑：

**指標選擇器 bug**：`.slice(0,30)` 上限疊加排序，讓 69 個可觸發指標裡有 39 個永遠選不到，使用者自己發現「感覺沒有全部進來」，不是錯覺，改成搜尋式 combobox 修掉

**字體/配色一致性**：後台側欄跟建立回測標題字體不一致（serif vs mono）統一成 mono；色彩改成台灣慣例紅漲綠跌（CSS 變數命名不變，只換十六進位值）

**OHLCV/MA 資訊條 + MA 疊圖**：
- 圖表左上角浮動資訊條，`subscribeCrosshairMove` 驅動，開高低收量整排顏色跟著那根紅/綠
- MA5/10/20/60/100/240 六條，client 端用 rolling window 算，`ISeriesApi` 六條都先建好用 `visible` 開關（不是動態新建/刪除 series），避免切換時整個圖表閃爍重建
- 「全開/全關」原本做兩個按鈕，使用者嫌占空間，改成單一按鈕依目前狀態（`every` 全開嗎）動態顯示文字＋切換，個別勾選跟批次按鈕互不鎖死

**XQ 式滾動軸——這是這次踩坑最多的一段，四輪連續修**：
1. 第一版簡單 `<input type="range">`，使用者反映「跟原生縮放打架」——根因是拉桿跳轉後 `fitContent()` 蓋掉使用者滾輪縮放的根數
2. 改成自訂 thumb 拖曳元件（軌道+可拖動色塊+根數徽章），改用「跳轉前記住可視根數、跳轉後套用同樣根數」邏輯，結果數字跟畫面對不上（`2639→1499`）——根因是跳轉一律只抓 `INITIAL_CANDLE_LIMIT=1500` 根新資料，縮放根數比這個寬就被硬夾，改成抓取量動態跟著縮放根數放大
3. 往右微調一次跳好幾天——根因是「右邊界自動補資料」呼叫 `series.setData()` 後，lightweight-charts 自己的「追最新資料」行為會把可視範圍推向新邊界，又立刻重新觸發同一個補資料條件，連環觸發。修法：右邊界補完資料後明確把可視範圍設回原本位置，不讓圖表庫自己接管（左邊界補資料其實一直都有做這件事，只是右邊界那段當初漏寫）
4. 縮放最小值沒有下限、拖曳熱區只有 thumb 本體（4~14px）很難點中——改用 `maxBarSpacing`（容器寬度 ÷ 30）限制最細縮放跟 XQ 一致；拖曳事件改掛在整條軌道（~740px）而不是只掛 thumb 本體，任何位置按住都能拖
5. 拖超過資料集邊界變空白——`around=` 查詢超出實際最後一筆會回傳 0 筆卻直接套用；改成抓空自動退回最後可用的一段，不留白畫面
6. 加了 `|<`／`>|` 兩個按鈕跳到最早/最新一筆，維持目前縮放根數、留 3 根空白邊界，不貼死畫面邊緣
7. 根數顯示數字用「寬度四捨五入」跟肉眼數的對不上（頭尾兩根常只露出一部分），改用 `ceil(to)-floor(from)`，比較接近但講明這是近似值不是像素級精確

**交易定位**：點交易明細列 → 原本沿用一般跳轉（維持目前縮放），使用者反映縮放太寬時金色標記淹沒在密集訊號堆裡找不到——改成獨立的 `jumpToTrade`，固定縮放到 100 根、盡量置中在進場那根，前後資料不夠置中時往有資料的那邊挪而不是硬置中；同時交易明細那一列跟圖表上對應的 B/S 標記都會變金色（`SELECTED_MARKER_COLOR`），用 `entry_time+direction+exit_time` 三個欄位比對是不是同一筆

**時區顯示 bug（重要，影響所有時間顯示）**：圖表 X 軸顯示 UTC、交易明細表顯示本地時間（瀏覽器 `toLocaleString` 預設行為），兩邊對不上，一度誤判是「跳轉跑到不相干位置」。lightweight-charts 把數字型 time 一律當 UTC 排版座標軸，不會轉本地時區。修法：`toChartTime`/`fromChartTime` 把餵給圖表的所有時間統一加上 `-getTimezoneOffset()*60` 秒的位移，讓圖表庫「以為自己在顯示 UTC」時顯示出來的數字其實就是本地時間；從圖表拿時間回來（十字準星、可視範圍）要用 `fromChartTime` 換回真正的 unix time，影響到 K 棒/成交量/MA 線/標記四處 setData 呼叫跟拖曳/滾動軸兩處讀 `getVisibleRange()`

**曾經誤判的假 bug（教訓）**：一度以為 `rules` 欄位中文亂碼是資料庫編碼損壞，後來用「寫檔案再讀回來」的乾淨方式重查，發現源碼檔案跟資料庫裡的 UTF-8 bytes 其實都是對的，是自己 Windows Git Bash 終端機顯示中文的字碼頁問題，不是真正的系統 bug——之後懷疑編碼問題要先排除終端機顯示這個可能性，不要急著下結論

透過 SSH 讓使用者自己在 NAS 上查（沒有直接連線 NAS，全程由使用者貼指令結果回來）：

- 舊站架構：前端是 `npm run build` 產物（`index.html`+`assets/`）直接 SMB 複製蓋掉 `web/` 根目錄；後端是 `apps/backend` 建成 image（`hermesnote-backend`），container 綁 port 8000，前端寫死 API_BASE 打這個 port，nginx 沒有 `proxy_pass`，前後端是兩個獨立服務
- 確認 `hermesnote-frontend` 容器把整個 `/mnt/Hermesnote/web` 掛進去（不是分別掛資料夾），代表新的 `hermes/` 資料夾不用改容器掛載，改 `nginx.conf` 的 `location /` 指過去、`docker exec ... nginx -s reload` 即可
- 決定：v2 完全取代舊站，port 8000 釋放給新的用；舊資料（`apps/`、`assets/`、`index.html`）搬進新建的 `archive/`；`python/`（還有 cron job 依賴）、`nginx.conf`（正在用，改內容不搬移）、`nee/`（太太的獨立網站）都不動
- v2 部署結構定案：`hermes/frontend/`＋`hermes/backend/`，跟本機開發資料夾對稱
- 寫了 `backend/Dockerfile` 草稿（`python:3.12-slim`＋編譯 TA-Lib C library 0.4.0＋`pip install -r requirements.txt`），還沒實際 build 測試過
- 查到舊的 `hermesnote-backend` 容器有掛 GPU passthrough（`Count:-1`, `Capabilities:[["gpu"]]`）——v1 把「跑網站 API」跟「需要 GPU 的東西」塞在同一個容器
- 重要環境事實：NAS 只有一顆實體 GPU（RTX 5060 Ti 16GB），且有一個地端 12B 模型（推測是 ollama 服務的）平常會用到這顆卡，用到時幾乎沒有餘裕同時做別的運算
- **架構決策：v2 web API 容器（登入＋回測）跟訓練容器分開（選項 B）**——理由是使用者確認未來要串接即時交易 API，即時交易不能被訓練炸掉的 process 拖累；GPU passthrough 允許多容器同時請求同一顆實體 GPU，不是「一顆卡只能一個容器」，拆容器純粹是架構選擇不是硬體限制
