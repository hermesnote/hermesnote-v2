## 下半場：後台登入 + 量化回測從單指標進化到多空策略引擎

> 同一天（2026-09-02）延續到隔天凌晨，內容量很大，跟上半場分開記。

### 後台登入：Google OAuth + email 白名單

- 決策：後台只有 Hermes（可能+太太）在用，不做 DIY 帳密系統，直接用 Google OAuth 驗證身分，後端檢查 email 是否在白名單（`.env` 的 `ADMIN_EMAILS`），過了就發自己簽的 session JWT（12 小時效期）
- 實際帶著使用者在 Google Cloud Console 一步步操作完成：新建 `hermesnote` 專案 → 設定 OAuth 同意畫面（外部、測試模式）→ 建立 OAuth 用戶端 ID（網頁應用程式，JS 來源 `http://localhost:5174`）→ 加測試使用者
- 後端：`backend/auth.py`（驗證 Google ID token、白名單檢查、簽發/驗證 JWT）、`backend/routers/auth.py`（`POST /api/auth/google`、`GET /api/auth/me`）
- 前端：`AuthContext`（token 存 localStorage）、`RequireAuth`（路由保護殼）、Google Identity Services 登入按鈕頁
- **踩到的 bug**：`main.py` 先 import 了 `routers/auth.py`（間接 import `auth.py`），`auth.py` 模組層級就讀了 `os.getenv("GOOGLE_CLIENT_ID")`，但這時候 `load_dotenv()` 還沒被 `main.py` 呼叫，讀到空字串，快取住，導致 Google 回報「audience 不對，預期是空字串」。修法：`auth.py`（以及後來的 `services/quotes.py`）自己在檔案開頭呼叫 `load_dotenv()`，不依賴 import 順序，這個 pattern 之後新模組都要照做

### 後台整體外殼

- `AdminLayout.tsx`：頂部列（跟前台共用同一個 logo lockup 元件，抽成 `LogoMark.tsx`）+ 左側欄（交易系統／模型訓練／量化回測／家庭理財）+ 右側內容區，巢狀路由切換
- 頭像選單（點頭像彈出「帳號設定」佔位＋「登出」），不是分開放頭像跟三個點兩個元件
- 「家庭理財」是記帳 Agent 專案在後台的入口，不是「記帳」（避免名字顯得太小，之後會長出理財規劃/現金流評估功能）

### 指標登記表：TA-Lib 161 個機械式產生

- `backend/indicators/registry.py` 用 TA-Lib 的 `abstract.Function` API，把 161 個函式的名稱/參數 schema/輸出線名稱機械式列出來，不是手key的，跟 `library.md` 的官方分組數字逐一核對一致
- `GET /api/indicators` 把整份登記表吐給前端
- 加了 `backend/indicators/descriptions.py`：161 個函式的中文一句話說明，人工撰寫（TA-Lib 本身沒有說明文字），透過 registry 的 `description` 欄位一起吐出去；`docs/library.md` 也同步補齊，兩邊要一起維護

### 訊號模板：從「只有 RSI」到「三套模板涵蓋 69 個指標」

- `indicators/signals.py` 三套通用模板：
  - **型態辨識**（Pattern Recognition，61 個）：TA-Lib 輸出本來就標準化成看漲(>0)/看跌(<0)/無(0)，直接當訊號
  - **震盪指標門檻穿越**（RSI、CCI、WILLR、MFI、ULTOSC、CMO、STOCH，7 個）：查證各自合理的超買超賣門檻值，共用「跌破下界/突破上界」模板
  - **交叉型**（MACD）：兩條輸出線互相穿越
- 其餘 92 個指標沒有「觸發模板」，但透過 `indicators/filters.py` 的通用門檻比較機制，161 個全部都能當「過濾條件」（不決定時機，只回答「現在符不符合」）——這個「觸發 vs 過濾」的二分法是這次討論收斂出來的核心概念

### 組合邏輯：從「A組/B組」到「進場/出場運算式」再到「多空四棵樹」

這段經過三次重新設計，每次都是使用者用完上一版之後才發現不夠用，記錄一下演進過程，避免以後重蹈覆轍：

1. **v1（A組/B組）**：A 組是觸發指標（AND/OR 鏈接），B 組是過濾條件（整組選 and/or/weighted 一種模式，只擋進場）。使用者用了之後發現：固定角色太死，未來策略組合可能 6 個 A、7 個 B，需要自訂分組
2. **v2（進場/出場運算式）**：拿掉 A/B 固定角色，改成「進場運算式」「出場運算式」各一棵可無限巢狀的 AND/OR/加權條件樹，同一個條件可以自由放進任一棵樹。做法參考了實際 survey 幾個回測平台（TradingView/QuantConnect/MetaTrader/FinLab/TEJ/Portfolio Visualizer/BigQuant/TrendSpider/Zerodha Streak）的介面設計，最後借用 **TrendSpider** 的遞迴群組樹（群組可以巢狀加子群組）跟 **TEJ Pro** 的加權模式共存、**Zerodha Streak** 的白話文即時預覽
3. **v3（多空四棵樹，目前版本）**：使用者指出期貨本身雙向都能做（不像股票放空要券），不該只做多方。改成「進場」拆成「多方進場/空方進場」、「出場」拆成「多方出場/空方出場」共四棵樹，左右版面對半（LONG／SHORT），SHORT 有一個「啟用」開關（不強迫每次都要設空方）。技術上剛好對應 vectorbt `from_signals` 需要的四條訊號（`entries`/`exits`/`short_entries`/`short_exits`），不是巧合是設計對了
   - 每個觸發指標算出的「上升方向」「下降方向」兩個事件，依放進哪個位置自動對應（多方進場/空方出場用上升方向，多方出場/空方進場用下降方向），使用者不用自己選方向

後端對應檔案：`indicators/tree.py`（條件樹遞迴求值，取代掉的 `indicators/combo.py` 已刪除）、`services/backtest_demo.py` 的 `compute_strategy_backtest`（四棵樹版本）、`routers/strategy.py`（`POST /api/backtest/strategy`）

### 其他修正

- `_stat()` 讀 vectorbt 統計值時，沒有虧損交易會讓獲利因子變成無限大，`pd.notna()` 檔不住 `inf`，直接讓整支 API 500；補上 `np.isfinite()` 檢查
- `symbol`/`timeframe` 拼 SQL 表名前補上白名單正則驗證（原本就有的 SQL injection 風險，這次一起補）
- **Windows 上 Vite 開發伺服器的檔案監控不可靠**：一次寫多個新檔案或整支檔案重寫時，容易讓 HMR 斷掉但不報錯，瀏覽器端強制重新整理也救不回來，必須真的重啟 `npm run dev` 進程（甚至清 `node_modules/.vite` 快取）才會生效。這次踩了三次才確立這個 pattern，之後大改前端要主動重啟伺服器再讓使用者測，不要讓使用者自己懷疑是不是電腦問題
