## 訓練系統設計討論——內容本身仍有效，重新歸位記錄於此

以下是今天實際討論出的內容，扣掉上述搞錯地方的部分，設計本身跟既有決策不衝突：

### V1 的三階段流程 + data leakage 防範——確認為「設計原則參考」，不是「程式碼沿用」

V1（`D:\hermesnote\backend\ml\train.py`）現行做法：
- **訓練**：train+val 期間，`split_mode='random'` 對這段做隨機打散分配 train/val
- **回測（in-sample）**：同一段期間改成時間序全期推論
- **測試（holdout）**：`test_start` 之後連續、完全沒訓練過的一段，永遠時序，不受 split_mode 影響
- **Data leakage 防範**：正規化只用 train 集統計量 fit，val/回測/測試階段一律沿用 train 算出的參數做 transform，不重新 fit

Hermes 明確要求：這**三階段流程的設計原則**與**data leakage 防範的原則**是教授要求、不可變動的規則，V2 訓練系統要延續同樣的原則。但**不是要 V2 直接沿用或 import V1 的程式碼**——V2 是乾淨重寫，V1 只作為理解「這個原則具體怎麼落地過」的參考對象，V2 要用自己的分層方式（router/service/repository）重新實作同樣的原則。

### 訓練架構 component 化：收斂為「2 種節點 + DAG 圖」設計

背景：V1 現行用 `mode` 字串（`single`/`mtf_stacking`/`mtf_multiscale`）if/elif 分流不同的時間框架×模型組合，每加一種新組合就要複製大量邏輯、改動範圍牽連整段程式碼，是 Hermes 認為「V1 完全沒有彈性」的具體根源。

V2 訓練系統的目標設計（尚未實作，這是這次討論收斂出的架構方向）：

- **Feature Node**：輸入時間框架＋特徵規格（單一指標／分組／消融集，或未來從量化回測有效策略組合匯出），輸出一個特徵陣列。各 Feature Node 各自獨立計算，即使用同一組特徵規格也不強制共用計算結果。
- **Model Node**：輸入一個或多個陣列（可來自 Feature Node，也可來自其他 Model Node 的輸出）＋架構＋超參數，輸出訓練好的模型＋預測陣列。每個 Model Node 是獨立實例，即使架構名稱相同（例如三個時間框架各自訓練一個 LSTM），彼此權重不共用。
- **不需要獨立的「融合」節點類型**：stacking 的 meta-model 本質上就是一個 Model Node，只是輸入來源是其他模型的輸出而非原始特徵——融合邏輯直接用 Model Node 表達即可。
- 整個實驗＝這些節點連接成的一張 DAG，不是固定的「單/多 TF × 單/混合模型」矩陣。新增組合方式＝新增一份圖規格（JSON，節點 + 各節點的 `inputs` 引用其他節點 id），不用改動執行引擎程式碼；執行順序用拓樸排序（先算無依賴的 Feature Node，再算依賴已完成節點的 Model Node）。
- Hermes 具體案例確認彈性上限：3 個模型（LSTM/LSTM/LSTM、Transformer/Transformer、XGBoost）分吃 1m/5m/15m/30m/60m/daily 共 6 個時間框架，各自輸出訊號，6 個訊號再餵給第 4 個模型（LSTM）做最終融合——這種任意排列組合是設計要撐住的彈性上限。

**效益與風險已對 Hermes 講清楚並取得認可**：
- 效益：新增時間框架組合／模型架構／特徵分組，都只是新增 JSON 資料，不用改執行引擎程式碼
- 風險：① 圖執行引擎本身是一次性大工程，比 V1 現行分支寫法複雜 ② 前台 UI 要跟著換成能組圖或至少多組配置的介面 ③ 系統要驗證 JSON 合法性（節點 id 存在、無循環依賴、輸出陣列形狀能否對齊拼接），沒做好可能訓練跑到一半才發現設定錯誤、浪費 GPU 時間
- 保護得到：新組合不用大改架構。保護不到：不符合「吃陣列→吐陣列」邏輯的需求（例如需要原始價格以外資訊、或需要依上一步結果動態決定要不要跑下一步的條件分支邏輯），屆時仍需擴充節點定義

### 即時交易系統與訓練系統的範圍界定

- **推論（inference）**：訓練與即時推論可共用同一張圖／同一套執行引擎，差別只在有沒有要更新權重。此為 DAG 設計額外帶來的好處。
- **交易決策（進出場判斷、持倉狀態、風控）不在這張圖裡**：圖的終點是輸出訊號，拿到訊號後要不要下單、加減碼、停損等，是圖以外的獨立一層，對應 V1 現有的 `backend/trade/decision.py`（交易模擬器）跟 `train.py`（訓練/模型）本來就分開的做法。
- **有狀態/條件分支邏輯**（例如「有持倉走出場判斷、空手走進場判斷」）超出這次圖設計的靜態順序執行假設，若未來需要，應在圖執行完、拿到訊號後另外用規則引擎或狀態機處理，不要求圖本身支援分支。
- **Hermes 確認的三階段工作順序**：① 模型特徵訊號（目前 focus，即上述節點圖設計）→ ② 模擬交易（策略邏輯）→ ③ 真實串接即時交易 API。三層架構上互相獨立，可依序推進。
