## 容器架構定案並落地

三個容器，一律用 `hermesnote-` 前綴（沿用網站識別，不是文件夾名稱）：`hermesnote-frontend`（nginx:alpine）、`hermesnote-backend`（web API，不掛 GPU）、`hermesnote-training`（訓練 worker，掛 GPU）。用 docker compose 統一管理，取代 V1 時代個別下 `docker run` 的方式。

**Deploy 腳本設計原則（Hermes 明確要求，重要）**：`deploy.ps1` 只負責「部署程式碼」，永遠不負責容器的建立/刪除。部署前會先用 SSH 檢查三個容器名稱是否都存在且在跑，任何一個對不上就整支腳本直接中止，不會嘗試建立新容器頂上去——容器層出問題是獨立要排查的問題，不該被 deploy 悄悄用「順手建一個新的」蓋過去（V1 早期有過這種邏輯搞出問題的前科，這次刻意避開）。

因此完整上線分成三個獨立階段：
1. **Container 清理**（一次性）：`docker stop`/`docker rm` 舊的 `hermesnote-backend`/`hermesnote-frontend`
2. **Container 建立**（一次性，不是 deploy.ps1 做的）：手動把程式碼透過 SMB robocopy 送上 `web/hermes/`，SSH 上去手動跑一次 `docker compose up -d --build`
3. **Deploy（`deploy.ps1`，之後永遠只跑這個）**：確認容器存在 → build 前端 → robocopy 複製 → SSH `docker compose up -d --build`（此時保證是「換新 image 更新」，不是「從無到有建立」）

## GPU/CUDA 驗證通過（本次最大的技術風險項，已排除）

- `docker-compose.yml` 的 GPU 設定第一次寫錯：用了 `runtime: nvidia`，這個寫法不等於舊容器實際在用的 `--gpus all` 機制（後者對應的正確 compose 寫法是 `deploy.resources.reservations.devices`），寫錯的結果是 `torch.cuda.is_available()` 回傳 `False`，容器裡也找不到 `nvidia-smi`
- 改成 `deploy.resources.reservations.devices`（driver: nvidia, count: all, capabilities: [gpu]）後重建，**確認 `torch.cuda.is_available() == True`，且正確認到 `NVIDIA GeForce RTX 5060 Ti`**——訓練容器的 GPU passthrough 這條路完全打通
- 訓練容器目前跑的是佔位訓練函式（`training/worker.py` 的 `run_training_placeholder`，一個會真的動用 GPU 做矩陣運算的測試，不是真正的訓練邏輯），已透過塞測試任務進 `model_training_jobs` 表驗證整條「排隊→GPU忙碌檢查→撿取→執行→寫回結果」的路徑正常運作

## `/hermes` 個人履歷頁上線（Codex 產出，靜態頁整合）

- 來源：`D:\Claude\output\interview-demo\interview.html`（Codex 產出，2.4MB 含 base64 圖片，六個專案中四個圖片完整，`Hermesnote`／`金融時間序列預測模型應用研究` 兩個目前是占位，等訓練功能＋Hermes Agent API 做出來再補，不急）
- 整合方式：純靜態頁，不轉 React，避開 SPA fallback——`nginx.conf` 加 `location = /hermes` 直接吐檔案，不受 React Router 影響
- 檔案分工（重要，之後 Codex 更新只需換一個檔案）：
  - `frontend/public/interview-resume.html`：Codex 每次產出直接覆蓋這份，履歷內容本身
  - `frontend/public/hermes.html`：外層包裝，站方 header（樣式完全比照 `Layout.tsx`/`Layout.css`，深色系、`Hermesnote` logo＋模型訓練/量化回測/Hermes 導覽）+ `iframe` 掛 `interview-resume.html`，`position: fixed` 固定在頂部、`body{overflow:hidden}`，履歷內容在 iframe 內部自行捲動，不會把 header 推走——這層以後不太需要再動
- 導覽列（`Layout.tsx`）加了 `Hermes` 連結指到 `/hermes`，用一般 `<a>` 不是 React Router `<Link>`，避免攔截
- **踩坑記錄**：第一次 deploy 後 `/hermes` 完全沒生效（顯示空白或舊快取），根因是 `frontend` 這個服務（nginx:alpine）沒有 build 步驟，`docker compose up --build` 不會因為 bind mount 的檔案內容變了就重建/重啟這個容器——nginx process 會一直用它啟動當下讀進去的舊設定，不知道檔案已經換了。修法：`deploy.ps1` 在 `docker compose up` 之後**每次都額外明講 `docker compose restart frontend`**，強制它重讀新設定/新靜態檔案。這是這次以後任何純靠 bind mount（不經過 build）更新內容的服務都要注意的坑。

**架構調整（同一天，第二輪）**：一開始 `/hermes` 是完全獨立的靜態 HTML（自己手刻一份 header，樣式抄 `Layout.css` 的數值），結果跟其他頁面的真實 header 在瀏覽器裡有肉眼可見的大小/間距落差（`clamp()`、`rem` 這類跟 viewport 相關的單位手抄很難完全對齊，而且以後 `Layout.css` 改了這裡不會跟著改，會一直漂移）。改成：`/hermes` 變成真正的 React Router 路由（`App.tsx` 新增 `<Route path="/hermes" element={<HermesResumePage />} />`，掛在跟 `/quant`/`/model` 同一個 `<Layout>` 底下），頁面內容是 `HermesResumePage.tsx`——一個全高全寬的 `<iframe src="/interview-resume.html">`，履歷本身還是維持 Codex 產出的純靜態檔案，只有外層 header 換成真正共用的 `<Layout>` 元件，保證跟其他頁面永遠一致、不會再漂移。因此拿掉了 `frontend/public/hermes.html`（獨立包裝檔）跟 `nginx.conf` 裡對應的 `location = /hermes`（不需要了，交回 SPA fallback 處理）。`interview-resume.html` 這個 Codex 換版時要覆蓋的目標檔案本身沒有變。
