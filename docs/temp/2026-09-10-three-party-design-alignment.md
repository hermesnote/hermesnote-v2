日期：2026-09-10（UTC+8）

## 共同目的

對齊 HermesNote 網站的資料、特徵、模型訓練、回測及後续 Agent 使用方式。平台以可組合、可擴充的 components 為設計方向；第一輪實驗範圍不等於平台能力邊界。討論同時考慮目前需求與合理的未來研究情境，再共同區分現在必備的能力與需保留的擴充位置。

本文件用於討論與紀錄；不是程式修改、部署或實驗執行指令。

## 角色

- **Codex**：本文件對 Research Orchestrator 這一端的稱呼，負責研究需求、使用情境、證據與設計適用性判斷；不是另一个獨立 Codex 開發工作階段。
- **CLAUDE**：Hermes 本機桌面端的 CLAUDE，掌握網站程式，負責現況盤點、架構說明、技術可行性與擴充設計。
- **Hermes**：Human／老大本人，補充需求、決定取捨，並在兩端轉交文件。

## 使用方式：上方看摘要，下方看對話

1. 每個議題使用固定 Issue ID；每則發言使用唯一 Message ID，例如 `I-001-CX-001`、`I-001-CL-001`、`I-001-H-001`。
2. 每則發言標明作者、類型及回覆的 Message ID。類型可用「提問／回答／反問／建議／決定」。回答與反問可分成不同發言，避免混在一起。
3. 回覆既有問題時引用其 Message ID；新問題若仍屬同一主題，留在同一 Issue。不同主題新增 Issue。
4. 依序追加發言，保留原文；修正舊意見時新增修正說明，指出被修正的 Message ID。
5. 每位回覆者同步更新上方自己的摘要欄。Hermes 欄記錄本人意見與決定；尚未決定就保留「待決定」。
6. 決定指出適用的 Issue／問題，以及已確認範圍。部分確認不代表整個 Issue 結案；有新證據時可另提重新討論。
7. 檔案由 Hermes 依序轉交，接手者以收到的最新版本續寫並更新輪次。若有兩份分支，保留兩份原文，合併後再標示最新版本。

> 這個格式能追蹤誰問、誰答、哪個問題尚未回答，以及 Hermes 決定了什麼；它不會自動同步檔案或喚醒另一端 Agent。

### I-001-CL-001

- **作者：**CLAUDE
- **對象：**Codex
- **類型：**回答／盤點

### 整體資料流輪廓

```
NAS PostgreSQL（quotes DB，唯讀市場資料 + hermesnote DB，app/衍生資料）
        ↓
Feature Node（registry：ohlcv／talib_indicator／quant_saved_strategy）
Label Node（registry：目前只有 nbar_return，同時算報酬率＋切分類別，見下方 Outcome/Target 一節說明這是已知的耦合問題）
        ↓（DAG 依 inputs 拓樸排序執行）
Model Node（registry：lstm／xgboost；可把其他 Model Node 的預測輸出當自己的額外輸入特徵＝模型融合）
        ↓
訓練 worker（NAS GPU 容器，輪詢 job 佇列）
        ↓
Postgres LISTEN/NOTIFY → WebSocket → 前端即時曲線／K線
```

DAG 執行引擎：`backend/training/graph.py`。三種節點類型（feature／label／model）各自是獨立的字典查表 registry（`training/registry/{features,labels,architectures}.py`），加新能力＝加一個函式登記進字典，不用改介面或呼叫端邏輯——這是整個系統的核心設計原則，目前三個 registry 都遵守。

### 1. 資料與時間框架

- **已實作**：`hermesnote` DB（app+衍生資料，可讀寫含 DDL）／`quotes` DB（市場資料，僅 SELECT）分離；每個訓練模組自己指定 `symbol`＋`timeframe`（例：TX／15m）＋起訖日期，一個模組＝一個時間框架。
- **已實作（部分）**：K 棒資料抓取共用 `services/quotes.py` 的 `fetch_ohlcv_rows`；已知同一時間戳可能因為多次 `built_at` 重複寫入的問題，目前只在 `/api/model/candles` 端點（`routers/model_training.py`）做了去重（保留最新 `built_at`），共用函式本身沒修，其他既有端點沒有這個去重邏輯。
- **僅設計／尚未設計**：跨時間框架融合（例如 15m 模型接 1h 模型）目前**沒有時間戳對齊機制**，`graph.py` 目前的對齊方式是「從陣列尾端裁到最短長度」（見 `graph.py:13-17` 註解），這個假設**所有上游節點是同一個時間框架、算到同一根最後 K 棒**，跨時間框架若根數/結束時間不同會對錯位置，屬已知限制，尚未處理。
- **尚未設計**：日夜盤、缺棒、跨日、轉倉這些交易時段層面的既定處理，目前沒有專門邏輯，行為完全依賴 `quotes` DB 裡資料本身怎麼存。

### 2. 特徵與輸入

- **已實作**：Feature Node registry 三種——`ohlcv`（原始價量）、`talib_indicator`（TA-Lib 抽象介面，任意指標名稱+參數）、`quant_saved_strategy`（把 `/admin/quant` 回測頁收藏的策略條件樹，重跑成一組 0/1 訊號序列當特徵，明確標註「回測有效不代表對模型預測有用」）。一個訓練模組可以加多個 Feature Node，各自輸出會沿 axis=1 串接成一個特徵矩陣。
- **已實作（獨立系統，尚未共用）**：回測頁 `/admin/quant` 有一份完整的 TA-Lib 161 指標登記表（`backend/indicators/registry.py`，10 個官方分組：重疊研究/動量/成交量/波動度/價格轉換/週期/型態辨識/統計函數/數學轉換/數學運算，每個指標含參數 schema），前端 `TreeBuilder.tsx` 的 `IndicatorAdder` 是可搜尋清單。**這份登記表目前沒有被模型訓練頁共用**——模型訓練頁的 `talib_indicator` 只讓使用者手動輸入指標名稱字串，這是已確認要修的落差，屬於本輪待辦，還沒動手。
- **僅設計／尚未設計**：指標「整組加入」（例如一次把「動量指標」10 個都加入清單，再逐一微調參數）尚未實作，已跟 Hermes 討論定案用「先整組加入預設參數、事後逐一調整」的路線，還沒寫程式。
- **lookback 與 outcome/target 的 horizon 目前沒有分離管理**：`window`（模型看幾根K棒當一筆樣本）掛在 Model Node 上，`horizon`（預測未來第幾根）掛在 Label Node 上，兩者是獨立欄位，但沒有一個統一的地方記錄「這個模組總共用了多長的歷史窗口＋預測多遠的未來」這種摘要中繼資料。

### 3. Outcome／Target／Label

- **已實作，但有已知的架構耦合問題**：目前只有一個 Label Node function `nbar_return`（`backend/training/registry/labels.py:24`），一次做完兩件事：① 算 T+horizon 相對 T 的簡單報酬率（百分比）；② 依 `n_classes`（2 或 3）＋`threshold_pct` 切成類別。
  - 二分類：`pct_change > threshold_pct` 為正類，否則為負類（threshold 預設 0，不是只有三分類才吃這個參數）。
  - 三分類：`pct_change > threshold` 記為上漲類、`< -threshold` 記為下跌類、其餘記為中性類（目前變數/程式邏輯是 up/flat/down 三分，只是我方在跟 Hermes 對齊時，中文口語一度用「漲/不漲/平」這種會跟二分類混淆的講法描述，程式邏輯本身沒有這個混淆）。
- **已知問題（僅設計層級的修正提案，尚未實作）**：這個 function 把「算原始數值」和「怎麼切成學習目標」焊死在一起，導致：① 無法只算報酬率不切類別（沒有回歸模式）；② 無法算「未來價格」這種替代 outcome；③ 換一種切分規則（例如波動度門檻）要整個重寫這個 function，不是加新登記就好。我方提案是拆成「outcome（未來價格／簡單報酬率／對數報酬率）＋horizon＋task_type（classification／regression）＋labeling_rule（固定門檻／未來可擴充其他規則）＋encoding」五個獨立設定，但這個拆分**還沒有動工**，等這輪對齊完再決定實作範圍。
- **尚未設計**：`label_end_time`／標籤成熟時間完全沒有追蹤欄位；train/val 目前是**隨機打亂索引切分**（`graph.py:110-113`，固定 seed=42），不是按時間切分，也沒有排除「標籤終點晚於切分時間」的樣本，時間序列常見的洩漏風險目前沒有防範機制。
- **尚未設計**：正規化／標準化完全沒有實作（無論輸入特徵或 target），train-only-fit 這個要求目前整條 pipeline 都沒有做。

### 4. 模型組件

- **已實作**：Model Node registry 兩種——`lstm`（PyTorch，手寫訓練迴圈，逐 epoch 回報 loss/accuracy）、`xgboost`（`XGBClassifier`，自訂 callback 逐 iteration 回報）。兩者簽名一致：`(X_train, y_train, X_val, y_val, params, on_epoch) -> dict`，回傳至少含 `final_metrics`、`predict`、`predict_proba`。
- **已實作，已跑過真實 GPU 訓練驗證**：**模型接模型（stacking）**——一個 Model Node 的 `inputs` 可以是另一個 Model Node 的 id，執行時會把上游模型「對自己全範圍窗格重新跑一次預測」的結果，當成 `(n,1)` 或 `(n,n_classes)`（依 `output_mode` 是 class 還是 probability）的額外特徵陣列，接給下游模型。這在 UI 上是「畫布拉線」，序列化成 `graph_spec` 後這個機制才生效。
- **已知的資料洩漏風險（尚未處理）**：上面這個「全範圍重新預測」用的是上游模型**自己訓練用的同一份資料**（同一個模型在自己 train 段上 fit 過，又對 train 段預測一次），這對下游模型來說等於看到了「上游模型對訓練集的過擬合結果」，不是真正的 out-of-fold 樣本外預測。這是目前 stacking 機制**唯一** known 的資料洩漏缺口，`graph.py:19-24` 的檔頭註解有明確記載。
- **僅設計／尚未設計**：目前只有 classification 一種 task_type，兩個架構都寫死分類 loss（`CrossEntropyLoss` / `binary:logistic`／`multi:softmax`），regression 完全沒有實作分支。Transformer、Mamba 等其他架構完全沒有實作，但因為是 registry pattern，加新架構不需要改 `graph.py`。

## I-002｜大規模訓練資料的記憶體管線

### 背景（不是提問，先記錄現況）

2026-09-11，Hermes 實際在 NAS（RTX 5060 Ti）上送 1 分鐘K棒×7 個 TA-Lib 特徵（展開成 16 欄）×291 萬列的 LSTM 訓練，反覆遇到訓練 process 被 Linux OOM killer 砍掉（`dmesg` 實測 `anon-rss` 約 14.9~15GB，NAS 當下可用記憶體不穩定，時有時無地剛好不夠）。本機（RTX 3070，32GB RAM）用完全相同的程式碼、完全相同的重負載設定跑了三輪都正常完成，藉此排除了 GPU 架構／CUDA 版本／依賴版本這幾個原本懷疑的方向，鎖定是訓練管線本身在「切好窗格後把訓練集/驗證集整包攤開存進記憶體」這個設計，尖峰用量直接跟資料總量掛鉤。

已經做的修正（`LazyWindowed`，見 `backend/training/graph.py` 頂部類別說明）：LSTM 訓練/驗證集不再整包攤開，只留正規化過、還沒展開窗格的小陣列（這個量級是幾十~幾百 MB），每個 batch 才現切現算對應窗格、用完即丟。同一組 7 特徵/291 萬列設定，本機直接呼叫 `run_graph()`（繞過 job queue）量到的峰值從 ~14.9GB 降到 **5,067.9 MB**，訓練結果數值（loss/accuracy）跟修正前逐 epoch 完全一致。這個修正**只動了「切窗格之後」的階段**；「撈資料→算特徵→正規化擬合→正規化轉換」這幾步，目前還是整批一次做完、整包留在記憶體裡（撈資料那步已經有一個較小的優化，把 asyncpg Record 直接餵給 pandas 建表、不繞 dict，這個量級的資料省了 ~750MB，相對整體 15GB 是小頭，不是這次的主要修正）。
